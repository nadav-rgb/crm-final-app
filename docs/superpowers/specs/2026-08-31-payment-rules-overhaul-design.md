# עדכון כללי תשלום — ידידותי/תורני, בונוס תורני, קשר קצרצר — מפרט תכנון

## מטרה

לממש בקשה של נדב (התקבלה בשעת לילה, "אל תעצור לשאלות — אני סומך על שיקול דעתך"): עדכון תעריפי קשר ידידותי/תורני עם כללי-זכאות חדשים, בונוס תורני חדש (1,000 ₪ לאחר 3 חודשים רצופים), סוג-קשר חדש "קצרצר" שאינו מזכה, ואימות שמפגש רב-משתתפים (שכבר קיים) עונה על הדרישה. **אין בשיחה אפשרות לשאול שאלות הבהרה** — כל החלטה עיצובית שלא מפורשת בבקשה המקורית מתועדת כאן במפורש עם ⚠️, לביקורת נדב בבוקר.

## החלטה קריטית שאינה מבוצעת אוטומטית: תעריפים ב-DB

`lib/paymentConfig.js` טוען תעריפים בפועל מטבלת `payment_config` ב-Supabase (עמודות `rate_phone_torani`, `rate_video_torani`, `rate_phone_friendly` וכו') — **לא** מהקבועים ב-`lib/paymentCalc.js`/`lib/paymentConfig.js`. אלה רק ה-fallback לכשל טעינה.

⚠️ **המשמעות:** שינוי הקבועים בקוד בלבד **לא ישנה שום דבר בפרודקשן** — הערך ב-DB גובר. אבל כתיבה שקטה ל-`payment_config` היא הפחתת שכר אמיתית ומיידית לפעילים אמיתיים (טלפוני-תורני 200→150, וידאו-תורני 250→200), בזמן שנדב ישן ולא יכול לאשר. זו בדיוק סוג הפעולה שהכללים שלי אוסרים לבצע בשקט גם כשמתבקש "לא לעצור לשאלות" — ההוראה ההיא הייתה על עמימות בעיצוב, לא על מוטציה על נתוני שכר אמיתיים בפרודקשן.

**החלטה:** אני **כן** מעדכן את קבועי ה-fallback בקוד (כדי שהתנהגות תהיה נכונה אם/כש-DB ריק או נטען מחדש), **וגם** מכין סקריפט מוכן-להרצה שמעדכן את שורת ה-DB (`scripts/apply-new-payment-rates.cjs`, בדפוס read+update עם `SUPABASE_SECRET_KEY`, כמו `scripts/mark-feedback-reviewed.cjs`) — אבל אני **לא מריץ אותו**. הדוח הסופי יסביר לנדב בדיוק מה הסקריפט עושה ואיך להריץ אותו ביודעין.

## ארכיטקטורה — שינוי חתימת calcInteractionPayment

`calcInteractionPayment` (הפונקציה שבודקת אם קשר בודד מזכה) לא מקבלת היום שום היסטוריה חוצת-חודשים של הלקוח — רק קשרים *מאותו חודש* (`prevContactMonthly`). כללי "3 חודשים ראשונים" ו"עבר לתורני" חייבים לדעת על ההיסטוריה המלאה עם הלקוח, לא רק החודש הנוכחי.

**הוספת פרמטר חדש, אופציונלי, בסוף הרשימה:** `calcInteractionPayment(interaction, prevContactMonthly, isHighPotential, prevActivistMonthly, cfg, contactContext)` כאשר:

```js
contactContext = {
  joinedAt: string|null,           // contact.joined_at
  allInteractionsWithContact: [],  // כל קשרי הפעיל עם הלקוח הזה, כל החודשים (למיון עוגן+תורני)
}
```

⚠️ **קריטי — פרמטר חדש = תקלה שקטה בכל קורא ששוכח להעביר אותו.** `contactContext = null` (ברירת מחדל) חייב להתנהג *בדיוק* כמו הכלל הישן (בלי הגבלת-3-חודשים, בלי ניתוק ידידותי אחרי תורני) — לא לזרוק שגיאה ולא "לנחש" תקרה מחמירה. זה מגן על קריאות ישנות שלא עודכנו מלקרוס, אבל **כל קורא אמיתי חייב להיות ברשימה למטה, בלי יוצא מן הכלל** — אחרת נוצר בדיוק דפוס הבאג שתועד כבר פעמיים ב-CLAUDE.md (מסך אחד מזהיר "חרגת", מנוע אחר משלם).

**רשימת קריאות ל-`calcInteractionPayment` שחייבות עדכון (כולן):**
1. `calcMonthlyPayment` (paymentCalc.js) — הלולאה הראשית
2. `paidBefore` (paymentCalc.js) — תצוגה מקדימה
3. `getMonthlyTotalForActivist` (paymentCalc.js)
4. `pages/contact/add-interaction/[id].jsx` — `payableCheck` (התצוגה המקדימה החיה בטופס עצמו)

בכל מקום, `contactContext` נבנה מ-`contacts.find(c => c.id === interaction.contact_id)` (בשביל `joined_at`) ומסינון `interactions` לפי `contact_id === interaction.contact_id && activist_id === activistId` (בלי הגבלת חודש).

## לוגיקת הזכאות לתשלום (בתוך calcInteractionPayment)

חדש, בתחילת הפונקציה (אחרי בדיקות derived/duration הקיימות, לפני בדיקת BASE_PRICES):

```
אם quality === 'ידידותי' וגם contactContext קיים:
  anchorDate = contactContext.joinedAt || min(date בכל contactContext.allInteractionsWithContact)
  אם אין anchorDate בכלל (לקוח בלי היסטוריה כלל, כלומר זה הקשר הראשון שלו) — anchorDate = interaction.date
  monthsSinceAnchor = הפרש חודשים קלנדריים בין anchorDate ל-interaction.date (0 = אותו חודש)
  firstToraniDate = התאריך המוקדם ביותר מבין contactContext.allInteractionsWithContact עם quality === 'תורני'
  אם monthsSinceAnchor >= 3:
    → not payable, reason: "קשר ידידותי — מעבר לחלון הזכאות של 3 חודשים מתחילת הקשר"
  אחרת אם firstToraniDate קיים וגם firstToraniDate <= interaction.date:
    → not payable, reason: "קשר ידידותי — הלקוח כבר עבר לקשר תורני"
```

מכסת 2/חודש/לקוח לפרונטלי-ידידותי (בנוסף לתקרה הכללית `PER_CONTACT_CAPS`, שנשארת ללא שינוי):

```
אם type === 'פרונטלי' וגם quality === 'ידידותי':
  friendlyThisMonth = prevContactMonthly.filter(i => i.type === 'פרונטלי' && i.quality === 'ידידותי').length
  אם friendlyThisMonth >= 2 → not payable, reason: "חרגת ממכסת 2 קשרים ידידותיים-פרונטליים בחודש עם לקוח זה"
```

⚠️ **סדר הבדיקות חשוב**: בדיקת חלון-3-חודשים/מעבר-לתורני קודמת למכסת 2/חודש — אם הקשר לא זכאי מלכתחילה (מחוץ לחלון), אין טעם לבדוק את המכסה. שתי הבדיקות לא סותרות: שתיהן "not payable", ההבדל רק ב-`reason` המוצג לפעיל.

## בונוס תורני — deriveToraniBonuses (חדש, lib/paymentCalc.js)

באותו דפוס בדיוק כמו `deriveMitzvotBonuses`/`groupMitzvotEvents`: פונקציה טהורה, מקור-אמת יחיד, נצרכת ע"י `lib/CrmStore.jsx` וסקריפטי ה-verify.

```js
function deriveToraniBonuses(interactions, contacts, amount = TORANI_BONUS_AMOUNT, months = TORANI_BONUS_MONTHS) {
  // 1. לכל (activist_id, contact_id): אסוף את כל (year,month) הייחודיים שבהם היה
  //    קשר עם quality === 'תורני' (מכל הפרויקטים בתשלום — countsForPayment).
  // 2. מיין כרונולוגית. מצא את הרצף הראשון של `months` (3) חודשים קלנדריים רצופים.
  // 3. אם נמצא — בונוס אחד, מיוחס לחודש השלישי ברצף (month = אותו (year,month) של
  //    החודש השלישי), amount קבוע (לא תלוי כמה קשרים תורניים היו בכל חודש — סף,
  //    לא ספירה מצטברת, כמו MITZVOT_BONUS_PER_LEVEL).
  // 4. אין רצף שני: ברגע שנמצא הרצף *הראשון*, מפסיקים לחפש ללקוח הזה — "פעם אחת
  //    בלבד לכל לקוח" (הדרישה המפורשת), ולא משנה כמה רצפים נוספים יש בהיסטוריה.
}
```

`bonus_key` לבונוס הזה: `makeBonusKey(activistId, 'בונוס-תורני', contactId, monthKey)` — נכנס ל-breakdown באותו דפוס כמו mitzvotBonuses/newParticipantBonuses (פרמטר רביעי חדש, אופציונלי, ל-`calcMonthlyPayment` — ⚠️ ברירת מחדל `[]` כדי לא לשבור קריאות קיימות; `lib/CrmStore.jsx` מוסיף `toraniBonuses` לרשימת ה-`useMemo` ומעביר אותו בכל הקריאות ל-`calcMonthlyPayment`, כמו `mitzvotBonuses`).

⚠️ **"רצופים" חוצה גם גבול פרויקט/פעיל?** לא — הבונוס הוא per (activist_id, contact_id), תואם לשאר מנוע התשלום שבו לקוח שייך לפעיל אחד. אם לקוח עבר בין פעילים, הרצף מחושב בנפרד לכל פעיל (כמו כל בונוס אחר במערכת).

## קשר קצרצר

**UI (`pages/contact/add-interaction/[id].jsx`):** שינוי "אופי הדיווח" משני כפתורים לשלושה: `👤 קשר עם לקוח` / `👥 מפגש רב משתתפים` / `⚡ קשר קצרצר`. כשנבחר "קצרצר": מוסתרים לגמרי בלוקי סוג-קשר, איכות-קשר, ומשך-זמן; מוצג רק `<select>` יחיד "אמצעי קשר" (טלפון / וואטסאפ). תיאור + פעולה הבאה נשארים (⚠️ ראה טבלת החלטות). `form.type` מוגדר אוטומטית ל-`'קצרצר'`, `form.quality` מקבל את הבחירה מה-dropdown, `duration_minutes` מוגדר אוטומטית ל-5 (קבוע, מתחת ל-`MIN_DURATION` בכל מקרה — לא שדה בטופס).

**מנוע (`lib/paymentCalc.js`):** בתחילת `calcInteractionPayment`, ליד בדיקת `isDerivedInteraction` הקיימת:
```js
if (type === 'קצרצר') {
  return { amount: 0, payable: false, reason: 'קשר קצרצר — אינו מזכה בתשלום' };
}
```
זה **חוסם תשלום במפורש** (לא סומך רק על `MIN_DURATION`/BASE_PRICES חסר — הגנה כפולה, בדיוק כמו העיקרון "defense in depth" שכבר קיים בקובץ הזה עבור שורות נגזרות). מכיוון ש-`'קצרצר'` לא תואם אף ביטוי `i.type === 'טלפוני'/'פרונטלי'/'וידאו'` בשום סינון-תקרה קיים במנוע, הוא **מוחרג אוטומטית** מכל מכסה/בונוס בלי שינוי נוסף — זו בדיוק הדרישה "אינו נחשב כמפגש מלא לצורך בונוסים או מכסות".

**`data/config.js`:** אין הוספה ל-`interactionTypes` (זה נשאר "סוג קשר" הרגיל) — "קצרצר" הוא מצב-אופי-דיווח שלישי, לא צ'יפ נוסף ברשימת הסוגים הקיימת. מוסיף קבוע חדש `CONFIG.contactMethods = ['טלפון', 'וואטסאפ']`.

## נתונים ישנים שעלולים להישבר

- **קשרים ידידותיים שכבר שולמו בעבר** (חודשים סגורים) — לא נוגעים בהיסטוריה, רק בחישוב *עתידי*. `calcMonthlyPayment` תמיד מחשב מחדש מהאפס לכל חודש; דוח של חודש עבר (למשל יולי) שכבר "נסגר" יחזיר סכום *שונה* אם מריצים אותו מחדש עכשיו (כי הכללים החדשים חלים רטרואקטיבית על כל חישוב, גם לחודש עבר) — ⚠️ זו נקודה אמיתית לבדוק: אם נדב כבר שילם שכר יולי לפי הכללים הישנים, הרצה מחדש של דוח יולי אחרי השינוי הזה "תראה" סכום נמוך יותר, לא כי שולם ביתר בפועל אלא כי הכלל השתנה. אין דרך קוד למנוע את זה (המנוע לא שומר היסטוריית-כללים לפי תאריך); זה נרשם כאן כדי שנדב יידע לצפות לזה ולא יבהל מהפרש בדוח של חודש שכבר שולם.
- **`contact.joined_at` חסר לחלק מהלקוחות הישנים** — הטיפול (fallback לתאריך הקשר המוקדם ביותר) מטופל בעיצוב למעלה.
- **קשרים ידידותיים-פרונטליים קיימים שכבר חרגו מ-2/חודש בחודש עבר** — לא משנה כלום בהיסטוריה, רק בחישוב-מחדש (כנ"ל).

## מחוץ להיקף

- לא מריצים את `scripts/apply-new-payment-rates.cjs` — רק מכינים אותו.
- לא נוגעים ב-`bonus_key` format הקיים לשום בונוס קיים.
- לא משנים את חוקי אירוח-שבת, וידאו-ידידותי, או תקרות המכסה החודשית הכלליות (`MONTHLY_CAPS`).
- לא בונים מחדש את מפגש-רב-המשתתפים — רק מאמתים שהוא עומד בדרישה (סעיף 4 בבקשה) ומדווחים.
- אין UI חדש לניהול `payment_config` מה-DB (מחוץ להיקף — לא התבקש).
